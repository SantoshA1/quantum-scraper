## gov 231 — the kill-switch stop leg had counted zero since birth

**Deployed:** Expansion Kill-Switch Monitor `awDk3AQesvO3SpQs` → version `793dec2c`
(prior `66d8471b`) · **Suite:** `tests/test-ksmon-stopleg-20260819.js` 8/8 + 2 sabotage runs
· **Live-verified:** execution 609191 (13:08 ET) runs the new predicate clean.

**Root cause — a case mismatch, the gov-216 defect family.** The stops CTE counted
`order_status = 'filled'`; the `quantum.order_events` writer stamps Alpaca-style
**`'FILLED'`**. The all-time status inventory contains **no lowercase value at all** — the
leg matched zero rows in the table's entire history. The witness is exact: on 08-18 the
four stop-outs (AES 09:32, DDOG 10:10, DUK 14:01, DASH 14:15) stood in `order_events` as
8 FILLED events / 4 distinct orders while execution **600258** (14:34 ET, 19 minutes after
DASH) evaluated `stop_fills_today=0, stop_trip=false`. The monitor ran perfectly all day —
210+ executions — and could not see a single fill.

**Second defect found while fixing the first:** each fill emits ~2 events. A naive case
fix (`count(*)`) would read 8 on 08-18 and trip the ≥4 bar at just **2** real stop-outs.
The deployed count is `count(DISTINCT coalesce(broker_order_id, order_event_id::text))`
— per order, NULL-safe (0 NULL broker ids to date).

**Verification matrix** (read-only, recorded in `docs/ksmon-20260819/verify-matrix-20260819.json`):
old predicate on 08-18 → **0**; new → **4**; today intraday → 0 (no deploy-day false trip);
the fixed leg would have tripped on exactly **5 days ever** (04-13, 04-20, 04-28, 07-24,
08-18) — a true tail-guard, not a twitchy one. Scope: only the stops CTE changed; the
n8n `{{ }}` templates, INSERT, gov-215 dedup guard, and thresholds are byte-identical
(KS-04/KS-05).

Semantics note, on the record: the leg is *named* `consec_stopouts` but has always been
*written* as a same-day count (a winner between stops does not reset it). gov 231 fixed the
counting, not the semantics — changing the definition is a PO/Conclave call.

## gov 232 — every gap/vix/surge override died at our own auth guard, anonymously

**Deployed:** main pipeline `vaqfCaELhOEWnkdo` → version **`27304305`** (chain: … 379178db
gov 227b → 27304305 gov 232) · **Suite:** `tests/test-ssm-override-auth-20260819.js` 10/10
+ 2 sabotage runs · deploy via subagent with before-gate sha check (draft matched
`db1ed3c2…` before patch); byte-verify `diff` exit 0; **scope-assert: exactly 1 of 150
nodes changed** (manifest-pinned).

**What the midday funnel called "AUTH_FAILED probes" was us.** The chain, from live
executions 608346 (DLR, gap-down −3.5%, SELL, conf 70) and 607166 (ABNB, gap-up +2.3%,
BUY, conf 47):

1. Ingress scrubs secrets off the item before it flows downstream (by design — payloads
   are logged) and stamps `_ingress_source` / `_tv_payload_shape` / `_original_alert_type`.
2. Sanitized scanner items authenticate at the SSM via the 2026-05-08 **handoff**:
   `alert_type` must be in the trusted list (HEARTBEAT, BROAD_SCANNER, …) plus the ingress
   stamps.
3. The **Gap News Detector rewrites `alert_type` to `EVENT_OVERRIDE`** when it promotes a
   STAND ASIDE into a BUY/SELL candidate — a value NOT in the handoff list. The `||` chain
   short-circuits on the rewritten value; `_original_alert_type='BROAD_SCANNER'` sat on the
   item, unread. → `AUTH_FAILED: Invalid or missing webhook secret`.
4. The guard's fail item replaces the payload with an anonymous marker → the audit
   writeback recorded **symbol UNKNOWN** — the kill was invisible even to the audit trail.

First exercised 08-17 (VIX-24 gappy tape started producing qualifying events): 3 + 6 + 3
override candidates died on 08-17/18/19. The feature — event overrides at 0.5× size — may
never have worked at all; 08-17 is simply the first day it fired. (The two examined
casualties, DLR and ABNB, were ticker-blocklisted and would have died at VC anyway; the
CLASS was dead regardless of merit.)

**Fix, three sites in the SSM auth block, nothing else:**
- the handoff type resolution now reads **`_original_alert_type` FIRST** — an override
  authenticates exactly like the scanner item it came from. **No new surface:** the same
  allowlist and the same `_ingress_source` + payload-shape gates are still required — a
  forged payload without the internal ingress stamps still fails closed (GS-05 proves it
  on both old and new bytes).
- both AUTH_FAILED return items now carry `ticker`/`symbol` — a failed auth leaves a named
  corpse in the audit instead of UNKNOWN (GS-09).

Every legacy auth path is proven byte-for-byte intact by executing the REAL auth region
offline: body-secret compare, GND-propagated header secret, TradingView fingerprint, plain
scanner handoff (GS-04/06/07/08; secrets in the suite are same-shape dummies — no
production value appears in any fixture).

**Live verification — landed within minutes.** The first post-publish execution
(**609443**, 13:35:04 ET) was itself a gap override: LYB gap-up +2.0%, conf 40,
`alert_type=EVENT_OVERRIDE`. On the new bytes it **authenticated**
(`_auth_method=upstream_auth_gate`) and proceeded through the full state machine, where it
was killed on MERIT — "Backtest insufficient: 0 trades (min 10)" — with complete
`_sm_gate_lineage`, factor attribution, and a named audit row. Exactly the designed
behavior: authenticate, then judge. The class that died 3×/day as an anonymous auth
accident is now governed signal flow.
